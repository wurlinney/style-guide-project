# Как внести изменение

Руководство предназначено для авторов документации сервиса подготовки к техническим собеседованиям. Предлагайте изменения через отдельную ветку и Pull Request (PR) в `main`.

## Подготовка и локальная сборка

Нужны Git и Python 3.12. Выполните команды в терминале:

```bash
git clone https://github.com/wurlinney/style-guide-project.git
cd style-guide-project
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m mkdocs serve
```

Если репозиторий уже склонирован, начните с перехода в его каталог. На Windows активируйте окружение командой `.venv\Scripts\Activate.ps1` в PowerShell. Откройте напечатанный сервером адрес. Для остановки нажмите Ctrl+C.

Сборка для публикации:

```bash
python -m mkdocs build --strict
```

Готовые HTML-файлы появятся в `site/`. Каталоги `site/` и `.venv/` в коммит не включайте.

## Предложение изменения

1. Опишите проблему: номер правила, непонятную формулировку, пример и ожидаемое улучшение. Можно создать issue или включить описание в PR.
2. Убедитесь, что локальные изменения сохранены. Перейдите в `main` и получите актуальное состояние.
3. Создайте ветку с понятным именем, например `docs/text-accessibility`.
4. Измените правило и связанные примеры. Проверьте терминологию и ссылки.
5. Запустите все проверки из следующего раздела.
6. Создайте коммит и отправьте ветку на GitHub.
7. Откройте PR в `main`, заполните шаблон и запросите независимое ревью.

Пример команд для новой ветки:

```bash
git switch main
git pull --ff-only
git switch -c docs/text-accessibility
```

## Проверки перед PR

Выполняйте из корня репозитория в активированном окружении:

```bash
python -m pymarkdown --config .pymarkdown.json scan --recurse README.md CONTRIBUTING.md .github/pull_request_template.md docs
python -m unittest discover -s tests -v
python -m mkdocs build --strict
```

PyMarkdown проверяет заголовки, списки, ограждения кода и базовый синтаксис. Ограничение длины строки отключено: длинный абзац переносится темой сайта автоматически. Повторяющиеся заголовки разрешены только в разных родительских разделах. Изменять остальные настройки без объяснения в PR нельзя.

Тесты извлекают Python-код из карточки задания и проверяют результат на пустом вводе, повторяющемся максимуме и других границах. При изменении примера обновляйте ожидаемые результаты по условию задачи. MkDocs собирается с `--strict`: предупреждения, включая повреждённые внутренние ссылки и пропуски в навигации, останавливают сборку.

Внешние ссылки проверяйте вручную. CI не подтверждает точность технических утверждений и доступность для всех вспомогательных технологий.

## Conventional Commits

Формат заголовка коммита:

```text
<type>(<scope>): <краткое описание>
```

`scope` можно опустить. Пишите, что изменилось; один коммит должен объединять связанную правку. Типы:

| Тип | Когда использовать | Пример |
| --- | --- | --- |
| `docs` | Правила, инструкции и примеры | `docs(accessibility): add text accessibility rules` |
| `fix` | Исправление ошибки | `fix(docs): repair training link` |
| `ci` | Сборка и публикация | `ci: deploy MkDocs to GitHub Pages` |
| `test` | Проверки примеров | `test: cover repeated maximum` |
| `chore` | Зависимости и обслуживание | `chore: update documentation dependencies` |

Для несовместимого изменения используйте `!` после типа или области и поясните последствия в теле коммита. При squash merge заголовок итогового коммита также должен соответствовать Conventional Commits. Проверку названий выполняет ревьюер; отдельного автоматического валидатора в проекте нет.

## Добавление раздела

1. Создайте Markdown-файл в `docs/`, например `docs/accessibility.md`. Имя файла пишите латиницей в нижнем регистре, слова разделяйте дефисом.
2. Добавьте один заголовок `#`. Используйте уровни `##` и `###` без пропусков.
3. Сформулируйте назначение, проверяемые правила и примеры. Для новых правил выберите уникальные идентификаторы; существующие не перенумеровывайте.
4. Добавьте файл в `nav` конфигурации `mkdocs.yml` под содержательной подписью. Путь указывайте относительно `docs/`.
5. Добавьте ссылки из связанных разделов и, если меняется руководство, обновите историю версий.
6. Проверьте сайт локально, включая узкое окно, клавиатуру, ссылки и поиск.
7. Выполните проверки, создайте коммит и откройте PR.

Пример записи навигации:

```yaml
nav:
  - О руководстве: index.md
  - Доступность текста: accessibility.md
```

Это фрагмент: добавьте строку в существующий `nav`, сохранив остальные страницы.

## Ревью и исправления

Автор указывает задачу, список изменений, результаты проверок и ограничения. Ревьюер читает дифф и собранные страницы, проверяет правила, понятность примеров, терминологию и ссылки. Содержательное замечание включает место, проблему или вопрос и, по возможности, вариант исправления.

Для учебного обмена отправьте ссылку на свой PR другому студенту и получите ссылку на его PR. Оставьте не менее трёх содержательных комментариев к PR партнёра. Не создавайте искусственные замечания ради количества: если ошибок нет, задайте вопросы о применимости правил и предложите обоснованные улучшения. Факты обмена фиксируйте ссылками на PR и комментарии в отчёте.

Автор отвечает на каждое замечание, вносит согласованные правки отдельным коммитом и повторно запускает проверки. Не переписывайте историю PR после начала ревью без согласования.

Пример сохранения исправления:

```bash
git add docs/accessibility.md
git commit -m "docs(accessibility): clarify alternative text examples"
git push -u origin docs/text-accessibility
```

Независимый ревьюер проверяет исправления и оставляет `Approve`. Сливайте PR только после одобрения, устранения блокирующих замечаний и успешного CI для последнего коммита. Самопроверка автора не заменяет одобрение партнёра.

## Проверка публикации

После merge откройте `Actions → Documentation` для нового коммита `main`. Убедитесь, что задания проверки и публикации завершились успешно. Откройте [сайт руководства](https://wurlinney.github.io/style-guide-project/), перейдите к изменённому разделу и проверьте текст. Если запуск завершился ошибкой, изучите лог проблемного шага, исправьте причину через PR и повторите проверку после merge.

## Обновление зависимостей

Прямые зависимости записаны в `requirements.in`, полный набор версий — в `requirements.txt`. Обновляйте их в чистом виртуальном окружении Python 3.12, устанавливайте `requirements.in`, затем сохраняйте `python -m pip freeze` в `requirements.txt`. Перед PR запустите все проверки. Не переносите в файл зависимости из общего рабочего окружения.
